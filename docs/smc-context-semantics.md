# SMC Context Semantics — Golden Oracle & Parity Contract

Phase 2 of the context bus-v3 track (see [smc-bus-roadmap.md](smc-bus-roadmap.md)).

This document is the semantic source of truth for the live context library
`SMC++/smc_context_engine_private.pine` (Phase 3, not yet written) and the
`SMC_Context_Bus.pine` producer (Phase 5). It defines, per domain, what each
field means, its warm-up / `na` / bar-close / age / persistence behaviour, and —
critically — **which fields have an exact Python source of truth (scoring parity)
and which are new Pine live-detection with no Python golden (spec only).**

Getting this split right is the whole point: porting a Python *scoring rule* is a
verifiable, golden-gated task; re-implementing *candidate detection* in Pine is
genuinely new work that must be specified and validated in Pine, not pretended to
be a 1:1 port.

## The two columns

| Column | Meaning | How it is validated |
|--------|---------|---------------------|
| **A — Scoring parity (Python golden)** | The rule operates on already-derived inputs. The Python reference is authoritative and frozen into `tests/fixtures/smc_context_golden.json`. | Thresholds: machine-checked against the Pine constants. Rule *logic*: the frozen `expected` values are what a port is read against — **not** executed against in CI. See below. |
| **B — Pine-native detection (spec only)** | Deriving the *inputs* the column-A rules consume (FVG geometry, sweep depth/volume, pool strengths, BOS/CHoCH structure) from live bars. No Python source of truth, or the Pine engine (`smc_engine_private`) is itself the SSOT. | Validated on TradingView (compile + visual scenarios); **not** golden-gated against Python. |

### What is actually gated — and what is not

Be precise here, because an earlier version of this document was not. It claimed a
*"Phase 3 compile/golden harness"* would reproduce the frozen values bit-for-bit.
**No such harness exists**, and none can run in CI: executing Pine requires
TradingView. Any reading of "the Pine port is golden-gated" was false.

What *is* mechanically enforced today:

| Check | Guard |
|---|---|
| Golden matches the live Python builders | `tests/test_smc_context_golden.py` |
| Frozen thresholds match the live Python constants | `tests/test_smc_context_golden.py` |
| **Frozen thresholds match the Pine constants** | `tests/test_pine_context_library_contract.py` |
| Every frozen threshold is ported to Pine **or** explicitly deferred with a reason | `tests/test_pine_context_library_contract.py` (`_NOT_IN_PINE`) |
| Thresholds are named consts in Pine, not literals at use-sites | `tests/test_pine_context_library_contract.py` |

What is **not** enforced: that the Pine *rule logic* reproduces the frozen
`expected` values. That is read-and-review plus on-chart validation. The threshold
check closes the hole that mattered most — a Python constant moving while Pine
keeps the old number, with CI fully green — but it does not prove the branches
match. Do not claim otherwise.

The golden file is generated by `scripts/gen_smc_context_golden.py`.

## Structure frame

- **Detection (Column B).** BOS / CHoCH / swing highs & lows / trend come from
  the Pine engine `smc_engine_private.detect_structure(simple int swing_len)` —
  the engine is the SSOT for structure. The Python `explicit_structure_from_bars`
  is a *separate* implementation, not a golden the Pine port must match. Do not
  golden-gate structure against Python.
- **Enrichment (Column A candidates, thin).** Event age (bars since last
  BOS/CHoCH), freshness flag, and "which S/R level is active" are simple
  derivations on top of the engine output; they are specified here and unit-checked
  in Pine, but carry no numeric Python golden.

**Confirmed-bar only.** The frame is rebuilt when `barstate.isconfirmed` and held
between ticks, so every field describes the last *closed* bar. `detect_structure`
raises its BOS/CHoCH alerts intrabar and they can vanish before the close — the
Suite gates the same alerts through `resolve_confirmed_signal` for this reason.
An ungated frame reports `bos = true`, `dir_event = ±1`, `bars_since_event = 0`
on a cross that then reverts.

**Warm-up / na:** structure is unavailable until `swing_len` bars exist. Anchor
bar indices are `na` (never `0`) when there is no event. Trend persists between
events.

- `trend` is `0` (unknown) until the first confirmed BOS/CHoCH. The engine
  bootstraps `var trend = 1` and only ever moves it on a CHoCH, so a raw
  passthrough reports "bullish" for every symbol before any structure exists.
  After the first event the direction has either been confirmed (BOS) or set
  (CHoCH), so `trend` is meaningful.
- `resistance` / `support` and their anchors are `na` until a swing pivot has
  actually been detected on that side. `detect_pivot` starts at `var x = 0` and
  `var trail_y = high`, so the raw values are `0` and the running high/low
  extreme — neither is a pivot.
- Availability is tracked from the engine's own `hh` / `swing_low` output, not
  from `x == 0`: the earliest real pivot anchors at `bar_index - swing_len`,
  i.e. bar_index `0`, so a bar-index test would discard a true pivot.

## Imbalance frame — Column A (Python golden)

Source of truth: `scripts/smc_imbalance_lifecycle.py::build_imbalance_lifecycle`.
Frozen thresholds:

| Constant | Value | Meaning |
|----------|-------|---------|
| `PARTIAL_MIT_PCT` | `0.5` | gap filled ≥ 50% → partial mitigation |
| `FULL_MIT_PCT` | `1.0` | gap fully closed → full mitigation (no longer active) |
| `LIQ_VOID_MIN_SIZE_PCT` | `2.0` | gap ≥ 2% of mid-price → liquidity void |

Rules (the Pine port must reproduce these exactly, applied to whatever FVG
objects `eng.fvgs_objects()` yields):

- **FVG mitigation:** `mit_pct = clamp(fill_depth / gap_size, 0..1)`; a bull FVG's
  `fill_depth = max(0, top − last_low)`, a bear FVG's `= max(0, last_high − bottom)`.
  Active while `mit_pct < 1.0`; partial when `mit_pct ≥ 0.5`.
- **BPR** = an active bull FVG and active bear FVG that overlap:
  `overlap_top = min(bull_top, bear_top)`, `overlap_bottom = max(bull_bottom, bear_bottom)`,
  active iff `overlap_top > overlap_bottom`. Direction `BULL` if
  `last_close > (overlap_top+overlap_bottom)/2` else `BEAR`.
- **Liquidity void** = any FVG whose `(top−bottom)/mid_price*100 ≥ 2.0`.
- **Composite `IMBALANCE_STATE` precedence:** `BPR` > `LIQ_VOID` > `FVG_BULL` > `FVG_BEAR` > `NONE`.

**Detection caveat (Column B):** the Python reference detects FVGs with a plain
3-bar rule (`bar[i].low > bar[i−2].high`). The Pine library will use the engine's
richer object-based `fvgs_objects()` instead, so the *set of detected FVGs* may
differ from the Python snapshot builder. Only the **rule layer above detection**
(mitigation %, BPR overlap, void %, state precedence) is golden-gated.

**na / 0:** inactive price levels (`*_TOP` / `*_BOTTOM`) are `na` on the bus, never
`0`. Counts default to `0`.

## Zone frame — Column B (spec only, no Python golden)

Order-block domain state. Distinct from [Zone bias](#zone-bias--column-b-spec-only-no-python-golden),
which is an **FVG** count rule living on the imbalance frame.

- **Detection (Column B).** Order-block candidate tracking, confirmation, ATR size
  filtering, breaking and discarding all come from the Pine engine
  `smc_engine_private.track_obs(...)` — the engine is the SSOT for order blocks
  exactly as `detect_structure` is for structure. There is **no Python builder for
  order blocks**, so this frame is *not* golden-gated: it is specified here and
  validated in Pine plus on-chart scenarios.
- **Enrichment (thin).** Newest-active selection, per-side counts, the new/broken
  edge flags, `ob_bias` and `state` are simple derivations over the engine output.
  They are specified here and structurally tested; they carry no numeric golden.

**Why this frame exists at all (it is not a v2 duplicate).** The v2 engine bus
already carries `ZoneObTop` / `ZoneObBottom`, but those are the *product's* best
**bull** order block only (`scan_active_bull_ob()` in `SMC_Long_Dip_Suite.pine`,
feeding the long plan). This frame is **direction-neutral**: it reports bull *and*
bear sides as one symmetric domain contract. The bear side is what v2 does not
have; the bull side is re-derived here so consumers get a single coherent frame
rather than a long-only product view stitched to a neutral one.

**Fields**

| Field | Meaning |
|---|---|
| `bull_ob_active` / `bear_ob_active` | at least one confirmed, unbroken OB on that side |
| `bull_ob_id` / `bear_ob_id` | engine id of the newest active OB on that side (`na` when none) |
| `bull_ob_top` / `bull_ob_bottom` | geometry of the newest active bull OB (`na` when none) |
| `bear_ob_top` / `bear_ob_bottom` | geometry of the newest active bear OB (`na` when none) |
| `bull_ob_count` / `bear_ob_count` | number of active OBs on that side (`0` when none) |
| `bull_ob_new` / `bear_ob_new` | an OB was **confirmed on this confirmed bar** |
| `bull_ob_broken` / `bear_ob_broken` | an OB **broke on this confirmed bar** |
| `ob_bias` | `+1` bull, `-1` bear, `0` neutral — see below |
| `state` | composite code — see precedence below |

**`ob_bias` is not `zone_bias`.** Same count-delta *shape*, different domain:
`ob_bias` compares **order-block** counts, `ImbalanceFrame.zone_bias` compares
**FVG** counts. They are separate fields and must never be aliased or merged.
`ob_bias = +1` if `bull_ob_count − bear_ob_count ≥ 2`, `−1` if `≤ −2`, else `0`
(reusing `ZONE_BIAS_COUNT_DELTA = 2`).

**`state` precedence:** `OB_BOTH(3) > OB_BULL(1) > OB_BEAR(2) > NONE(0)`.
`OB_BOTH` when both sides hold an active OB.

**Size filter.** OB candidates are bounded by ATR multiples mirroring
`SMC_Long_Dip_Suite.pine` (lines 904-906): `min = smc_lib_atr(ATR_LEN_MAIN) * 0.5`,
`max = smc_lib_atr(ATR_LEN_MAIN) * 2.5`, with `ATR_LEN_MAIN = 50`. `smc_lib_atr`
(not `ta.atr`) is used so the warm-up window matches the Suite — plain `ta.atr`
is `na` before `length` bars, `smc_lib_atr` falls back to the cumulative TR mean.

**Profile features stay off.** `capture_profile`, `align_edge_to_value_area` and
`align_break_price_to_poc` are left `false`, so the engine never builds a
`pe.Profile` and OB geometry is the raw `left_top` / `right_bottom`. The
`smc_profile_engine` import in the context library therefore exists **only** so
Pine can resolve the `pe.Profile` field declared inside `eng.OrderBlock`; the
library calls no `pe.*` function. This is a type-resolution edge, not a use of the
profile engine, and is enforced by `tests/test_pine_context_library_contract.py`.

**Warm-up / na / persistence:** no OB exists until the engine confirms one. Prices
and ids are `na` (never `0`) when that side holds no active OB; counts are `0`.
The engine removes broken blocks from the active buffer (`update_broken`), so an
OB is never simultaneously active and broken. `bull_ob_new` / `bull_ob_broken` are
**edges** — true only on the bar the event occurs, never latched.

## Sweep frame — Column A (Python golden)

Source of truth: `scripts/smc_liquidity_sweeps.py::build_liquidity_sweeps`.
Frozen thresholds:

| Constant | Value | Meaning |
|----------|-------|---------|
| `SWEEP_DEPTH_MIN_PCT` | `0.1` | min depth % for a valid sweep (and the quality point) |
| `SWEEP_VOLUME_RATIO_MIN` | `1.2` | sweep-bar volume vs average |
| `SWEEP_RECLAIM_MAX_BARS` | `5` | reclaim must occur within 5 bars |

Rules:

- **Type — two paths, and the first one is easy to miss.**
  1. **Passthrough (checked first).** If the row already carries a
     `sweep_type` ∈ {`STOP_HUNT`, `LIQUIDITY_GRAB`, `INDUCEMENT`}, it is returned
     **verbatim** and the derivation below is skipped entirely. A port that omits
     this branch re-derives and returns a *different* type — the
     `explicit_type_passthrough` golden fixture exists to catch exactly that.
  2. **Derivation (only when no explicit type).** `STOP_HUNT` if
     `depth ≥ SWEEP_DEPTH_STOP_HUNT_PCT AND vol_ratio ≥ 1.2`; else
     `LIQUIDITY_GRAB` if `vol_ratio ≥ 1.2`; else `INDUCEMENT` (when any sweep is
     present); else `NONE`.

  The depth gate is **inclusive** and is its own constant — a depth of exactly
  `0.3` clears it. It used to read `SWEEP_DEPTH_MIN_PCT * 3`, and `0.1 * 3` is
  `0.30000000000000004` in IEEE-754, so exactly `0.3` fell just short and
  classified `LIQUIDITY_GRAB`. That boundary was an artifact of the arithmetic,
  not a rule anyone chose; it was removed as its own deliberate behaviour change.
  Port `SWEEP_DEPTH_STOP_HUNT_PCT` as a named constant — do **not** re-derive it
  from `SWEEP_DEPTH_MIN_PCT`. The two answer different questions ("is this a sweep
  at all" vs "is it deep enough to be a stop hunt") and their coupling was
  incidental. Pinned by the `stop_hunt_depth_boundary` fixture and
  `test_stop_hunt_depth_gate_is_an_inclusive_clean_three_tenths`.
- **Direction:** single-side sweep → `BULL`/`BEAR`; both sides swept → resolved
  only by an explicit `sweep_bias_bull`, otherwise **`NONE` (ambiguous, never a
  silent default)**.
- **Quality (0–5, additive):** +1 any sweep, +1 type∈{STOP_HUNT,LIQUIDITY_GRAB},
  +1 reclaim active, +1 `depth ≥ 0.1`, +1 `vol_ratio ≥ 1.2`.

**Detection (Column B):** computing `sweep_depth_pct`, `sweep_volume_ratio`,
`sweep_reclaim_active` live from bars is new Pine work; the Python builder only
*scores* pre-computed rows. Reclaim within `SWEEP_RECLAIM_MAX_BARS` is a live
Pine detection detail with no Python golden. (This mirrors the sweep-trap shadow
work: producers reclaim inside the sweep bar itself — see the sweep-trap ledger.)

## Pool frame — Column A (Python golden)

Source of truth: `scripts/smc_liquidity_pools.py::build_liquidity_pools`.
Frozen thresholds: `IMBALANCE_SIG_THRESHOLD = 0.3`, `PROXIMITY_NEAR_PCT = 1.0`,
`CLUSTER_STRONG_COUNT = 3`.

(The latter two were previously live-but-unfrozen: `_quality_score` used them —
`CLUSTER_STRONG_COUNT` only by an inlined literal `3`, so the named constant
governed nothing — and neither appeared in `_meta.thresholds`, so both could move
without the parity contract noticing. Now wired and frozen.)

Rules:

- **Imbalance:** `buy = buy_strength + untested_buy`, `sell = sell_strength + untested_sell`;
  `POOL_IMBALANCE = round((buy−sell)/(buy+sell), 4)` in `[−1,+1]`,
  `0.0` when `buy+sell == 0`.
- **Magnet direction:** `UP` if `imbalance ≥ 0.3`, `DOWN` if `≤ −0.3`, else `NONE`.
- **Quality (0–5, additive):** +1 any pool level, +1 strength ≥ 3 either side,
  +1 proximity in `(0, 1.0]`, +1 cluster density ≥ 3, +1 `|imbalance| ≥ 0.3`.

**Detection (Column B):** deriving pool levels, strengths, untested counts,
proximity and cluster density from live bars/volume is new Pine work.

## Zone bias — Column B (spec only, no Python golden)

The plan's "zone bias = active FVG count difference ≥ ±2" is a count comparison
over the live imbalance frame (`BULL_FVG_COUNT − BEAR_FVG_COUNT`). There is no
dedicated Python scorer for it, so it is specified here and validated in Pine, not
golden-gated: `bias = BULL` if `bull_count − bear_count ≥ 2`, `BEAR` if
`≤ −2`, else `NEUTRAL`.

Despite the name this rule is about **FVGs**, and it lives on `ImbalanceFrame` as
`zone_bias`. The order-block equivalent is `ZoneFrame.ob_bias` (see
[Zone frame](#zone-frame--column-b-spec-only-no-python-golden)) — same `±2`
count-delta shape, different domain. Keep them separate.

## Global field conventions (all frames)

- **Bar-close.** All context fields are evaluated on confirmed bars; any bus
  publish and alert gating uses `barstate.isconfirmed`. No intrabar repaint.
- **`na` vs `0`.** Price levels are `na` when inactive — never `0` (a real price
  can be near `0` on some symbols; `0` as "off" would be a lie). Counts, scores,
  and enum-codes default to `0` / `NONE`.
- **Persistence.** States persist between events (a BPR stays active until
  mitigated); ages increment per confirmed bar; freshness decays.
- **Enums travel as small integer codes** on the bus; prices/percents/scores
  travel as their raw float value.
